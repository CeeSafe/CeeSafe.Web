# M8 — Reverse proxy: record

Implementation plan §7 (M8), plus M7's open items (the owner, 2026-11-03). Toolchain: ceesafec **0.11.0** (from stage 3, for U20; stages 1 and 2 were built and tested on 0.10.3). Design:
Web ADR 0012, accepted 2026-11-03 with each of its six recommendations.

**Status (2026-11-06):** the gate has passed (below), and M8 is on main (#3, `10fc4e6`); it is released with M9 as
v0.4. The ADR is accepted, with amendment 1 (`Client.run`, the owner's choice A).
- **Stage 1** is built: the HPACK encoder's dynamic table, request trailers, and half-close. Its h2spec check found
  that M7's "145/145" does not hold on every run. One cause is fixed (`9f0e5ee`); one is a timing case for the owner
  (Findings, below).
- **Stage 2** (the client) is built:
  - a request authority;
  - a response's fields and trailers;
  - a general Upgrade;
  - HTTP/2, with the engine's client role and `Client.run`.
- **Stage 3** (`web_proxy`, on `m8-stage3`) is built, on ceesafec 0.11.0:
  - forwarding fields and trusted proxies; the PROXY protocol, read by the connection worker;
  - choosing backends (smooth weighted round robin, two random choices, rendezvous hashing) and passive and active
    health;
  - the relay: request bodies streamed upstream (U20, resolved by 0.11.0), answers and trailers relayed, 502/503/504
    before the head, an aborted response after it, retries within a budget, upgrades tunnelled;
  - `ReverseProxy.route<S>()` on a route, `handler()` as the whole application; `examples/proxy`.
- The gate's interop checks pass (Runs). The parsers' fuzzer, `tests/fuzz/proxy`, is built; it found a way for a client
  to choose its own address past a trusted proxy, and five departures from the specifications, all fixed (Findings).
  Its 24 CPU-hour run on Debian ended clean.
- The 24 CPU-hour fuzz run of `web_http2` that M7 owed ended clean. `tests/fuzz/h2` now has the client role and HPACK's
  dynamic table (Web ADR 0012 §5). It found that a zero WINDOW_UPDATE on an idle stream drew an RST_STREAM, and
  writing its oracle showed that control bytes were let into field names; both fixed (Findings). Its 24 CPU-hour run
  on Debian ended clean. The owner kept the RST_STREAM for PRIORITY on an idle stream (Findings).
- On Debian, the gate's checks pass under epoll and io_uring: every package in every mode, the proxy gate and
  Autobahn. Under io_uring the proxy gate first found reads lost when a race's other value was dropped; fixed
  (`92f23fb`, Findings). The 0.17.0 release builds and passes M8 unchanged; 0.18.0 does not check it (CeeSafe B18,
  fixed upstream in 0.18.1, with which M8 checks unchanged; `docs/toolchain.md`).
- On Windows 11 ARM64 every package passes in every mode, after two tests' timing was made robust to Windows' 15.6 ms
  clock (Findings; CeeSafe U21).
- **Stage 4** (the gate): every item of Web ADR 0012 §5 has a test or a run (Gate, below). Writing them found three
  trailer bugs: an HTTP/1.1 response's trailers dropped, a request's never sent, and the `Trailer` field removed;
  all fixed (Findings). With them, the proxy gate passes 27/27 on macOS, every package passes in every mode with
  0.11.0 and with 0.18.2, and h2spec's §8.1.2.6 timing case stays as the owner decided.

## Findings

- **Fixed (stage 4): an HTTP/1.1 response's trailers were dropped when its whole body was written before the
  handler ended.** `Exchange.finish` declared the buffered body's `content-length`, which leaves nowhere to put
  trailers (RFC 9112 §7.1.2). The proxy relays a small upstream body that way, so the gate's curl check got `hello`
  without `x-checksum`. A response with trailers and no declared length is now chunked (HEAD and bodiless statuses
  keep the length). Test: `web_http1`'s `whole_response_trailers_need_chunks`, which fails without the fix.
- **Fixed (stage 4): the client could not send a request's trailers**, over either protocol, so the proxy dropped
  a client's (§3.10). `BodySource` gains `copyTrailers`. HTTP/1.1 writes them in the last chunk; HTTP/2 ends the
  stream with a HEADERS frame. Names that frame or route a message (`content-length`, `transfer-encoding`, `host`,
  `connection`, `te`, `trailer`, pseudo-fields), names that are not tokens and values with control bytes are not
  sent. Tests: `web_client`'s `request_trailers_in_the_last_chunk` and `request_trailers_end_the_stream` (decoded
  with the HPACK decoder: only `x-sum: 42` is sent, and END_STREAM is on the second HEADERS frame, not on DATA), and
  `web_proxy`'s `trailers_are_relayed_both_ways`.
- **Fixed (stage 4): the proxy removed the `Trailer` field.** RFC 9110 §7.6.1 does not make it hop-by-hop, and
  neither does Web ADR 0012 §3.5's list. It is now forwarded, and `trailers_are_relayed_both_ways` checks it.

- **Fixed: h2spec §5.1 #10 sometimes read a TCP reset instead of GOAWAY** (`9f0e5ee`). `H2Connection.sendData`
  checked the flow-control allowance before the stream's existence. A stream the client had reset has an allowance
  of 0, so a handler's DATA still on its way gave INTERNAL_ERROR instead of STREAM_CLOSED. The driver treats
  INTERNAL_ERROR as fatal: `serveH2` failed, the worker dropped the socket without `closeGracefully`, and h2spec's
  unread frames made the kernel send a reset. Test: `sends_after_the_peer_reset_are_stream_closed`, which fails
  without the fix.
- **Decided (the owner, 2026-11-04): h2spec §8.1.2.6 #1 and #2 are a timing case, and early responses stay.**
  They fail about 1 run in 10 over TLS and 1 in 4 over h2c.
  - The example's `/` answers without reading the body. If its response is written before the DATA frame whose
    length contradicts `content-length` arrives, h2spec sees HEADERS where it expects RST_STREAM or GOAWAY.
  - The stream is still reset when that DATA arrives.
  - RFC 9113 §8.1 lets a server send a complete response before the request is complete.
  - Holding every response until a body of declared length has ended would pass h2spec, but would delay exactly the
    early answers (401, 413) that §8.1 exists for.
  - The gate's "h2spec 100 %" is therefore read as: every case passes when the response does not race the request's
    body.
- **Fixed (amendment 2): the PROXY protocol's acceptor failed the allocation sweep.** It was an `Acceptor` calling
  its inner one through `dyn Acceptor`. That is a stacked await (CeeSafe ADR 0056), and allocation 9 of
  `the_acceptor` hit ADR 0056 §3.3's panic. On the owner's choice the connection worker reads the header instead,
  with no cycle. The worker test (`the_worker_reads_proxy_headers`) and the parser tests then have no failures in 105
  and 167 allocation-sweep runs.
- **Fixed: a request could wait forever when an HTTP/2 connection failed out of memory** (`754d2bd`, `web_client`).
  Found by the full run's allocation sweep: `two_requests_share_a_connection` timed out at allocations 86–123.
  - A connection that failed before its first frame left its command queue open.
  - A start `run` could not spawn a task for was dropped.
  - A stream that could not be opened or kept was never told.
  - A stream's inbox was dropped, not closed, so a request whose last part did not fit never saw the end.
  Each now tells the request and closes its channels; with the old driver the same allocations still hang.
- **Fixed: `/` never matched a root wildcard** (`web_server`, from M2). `Router.find` returned the root node for `/`
  even without routes there, so `/*path` (how `examples/proxy` mounts the proxy) gave a 405 with an empty `Allow`.
  Web ADR 0007 §3.3 and the existing tests let a wildcard be empty (`/files/` matches `/files/*rest`). Test:
  `a_root_wildcard_matches_the_root`, which fails without the fix.
- **Fixed: two `Date` fields in a proxied response** (`web_http`). The writer added its own `Date` beside the one the
  proxy relayed; RFC 9110 §6.6.1 gives a response one. A handler's `Date` now stands, over HTTP/1.1 and HTTP/2. Tests:
  `a_head_date_is_the_only_date` (the encoder) and `a_handler_date_is_the_only_date` (HTTP/2's heads, HPACK-decoded),
  which fails without the fix.
- **Fixed: a client could choose the address it is known by** (`b860e22`, `web_proxy`; found by `tests/fuzz/proxy`'s
  invariant 6).
  - A trusted proxy that extends the `Forwarded` field it received (nginx's `$proxy_add_forwarded`, and this proxy's
    own `forwardingFields`) appends its hop after the client's bytes.
  - The splitter toggled on every `"`, so an unclosed quote in the client's bytes, such as
    `for=203.0.113.9;x="`, swallowed the appended `, for=198.51.100.241`. The client's own `for=` was then the
    right-most hop, and `clientOf` named 203.0.113.9; with `for=_x`, the client hid.
  - A field that ends inside a quoted string cannot be split, so its last hop is now malformed and the walk stops at
    the trusted peer (Web ADR 0012 §3.4). A proxy's hop in a field of its own is read whatever the client's holds.
  - Test: `a_client_cannot_swallow_the_trusted_hop`, which fails without the fix.
- **Fixed: `Forwarded` read quoted strings and lists more narrowly than RFC 9110 §5.6** (`b860e22`). A `\"` ended a
  quoted string (§5.6.4 makes it a quoted-pair); a `for` value was not unescaped (RFC 7239 §5.2: "after potential
  quoted-string unescaping"); an empty list element was a malformed hop (§5.6.1.2: "MUST parse and ignore"). A second
  `for` in one element is now malformed (RFC 7239 §4). Test: `quoted_pairs_and_empty_elements`.
- **Fixed: the PROXY protocol's parser departed from proxy-protocol.txt** (`b860e22`, `web_transport`).
  - v1: after `UNKNOWN`, two spaces or more than five fields were refused; §2.1 says the receiver "must ignore
    anything presented before the CRLF".
  - v2: an unassigned family or transport was accepted, where §2.2 says such values "must be rejected as invalid by
    receivers". Addresses over the UNSPEC transport were used, where "the receiver should ignore address
    information". An AF_UNIX block shorter than its two 108-byte addresses was accepted, though "the receiver must
    also reject incoming connections containing partial protocol headers".
  - A zone was let through as `%0`, which lib/std parses as scope 0, in a TCP6 address, a CIDR block and a
    `Forwarded` node. Any `%` is now refused.
  - Tests: `unknown_ignores_the_rest_of_its_line`, `version_2_families_and_transports`, and new cases in `version_1`
    and `blocks_rfc4632`.
- **Fixed: control bytes were let into field names** (`6e6a37a`, `web_http2`; found while writing `tests/fuzz/h2`'s
  oracle for RFC 9113 §8.2.1). §8.2.1: "A field name MUST NOT contain characters in the ranges 0x00-0x20", and such a
  request or response "MUST be treated as malformed". `goodName` refused only NUL, CR, LF and SP, so a name with
  0x01-0x1F (but LF and CR) passed, in a request (to a handler, and through the proxy to an HTTP/1.1 backend) and in
  a response. Test: `control_bytes_in_field_names_rfc9113_8_2_1`, which fails without the fix.
- **Fixed: a zero WINDOW_UPDATE on an idle stream drew an RST_STREAM** (`6e6a37a`, `web_http2`; found by
  `tests/fuzz/h2`'s client mode). §6.9 makes a zero increment a stream error, but on an idle stream §5.1 makes any
  frame other than HEADERS or PRIORITY a connection error, and §6.4: "RST_STREAM frames MUST NOT be sent for a stream
  in the 'idle' state". The idle check now comes first, in both roles. Test:
  `zero_window_update_on_an_idle_stream_rfc9113_5_1`, which fails without the fix.
- **Decided (the owner, 2026-11-05): PRIORITY on an idle stream keeps its RST_STREAM.** A PRIORITY of a length other than 5 is a stream error
  (§6.3), as is one that depends on itself (§5.3.1), and PRIORITY may name an idle stream; yet §6.4 forbids
  RST_STREAM for an idle stream. The engine sends the RST_STREAM (`priorityFrame`), and the fuzzer allows it there
  only. Options: keep it (the text of §6.3); or end the connection with PROTOCOL_ERROR or FRAME_SIZE_ERROR instead
  (§6.4's ban kept, at the cost of a connection the peer only mislabelled). Kept, as recommended: §6.3 is the more
  specific rule, and a peer that sent the frame cannot be confused by a reset of a stream it named. No code change.
- **Fixed: reads lost under io_uring when a race's other value was dropped** (`92f23fb`; `web_http2`, `web_client`,
  `web_ws`, `web_sse`, `web_proxy`; found by the proxy gate on Debian with `CEESAFE_REACTOR_URING=1`).
  - `Async.race` returns the loser's value as `other` when it also finished. Under io_uring, a read cancelled as
    another arm won may already have completed, and then returns its bytes (CeeSafe ADR 0035 §3.4). A channel
    receive does the same with what it took.
  - The connection loops dropped `other`, so those bytes were lost and the framing broke. h2c request bodies past
    the 64 KiB window broke off, and `h2load` had 90 of 20 000 requests errored. Under epoll the same checks
    passed.
  - `serveH2`, `web_client`'s HTTP/2 connection and `web_ws`'s session now handle both values. Inner
    message-or-timer races (also `web_sse`'s and the proxy's tunnel) keep the message when the timer won, and the
    read when the idle timer won. In `web_client`, a start token taken as the drain began still starts.
  - Tests: `MockTransport.withCompletingReads` gives a paused read that completes even when cancelled. The tests in
    `web_http2`, `web_client` and `web_ws` that use it fail without the fix.
- **Fixed: two tests assumed millisecond timers, and failed on Windows** (test code only).
  - `Timer.now()` on Windows advances once a tick, about 15.6 ms (CeeSafe U21): a 1 ms sleep lasts about 25 ms.
  - `web_http2`'s `a_read_completed_as_it_was_cancelled_keeps_its_bytes` feeds about 1 250 bytes 7 a read, each
    read pausing 1 ms. On Windows that took about 4.5 s, and the scripted client closed at 2 s, before the request
    had been read. In pieces, its close now counts from the last input byte read.
  - `web_sse`'s `heartbeats_while_quiet` (from M3) had 25 ms between the second heartbeat and the event. Heartbeats
    are now 100 ms apart and the event comes at 250 ms: 50 ms on either side.
