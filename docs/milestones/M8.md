## Findings

- **Fixed: h2spec §5.1 #10 sometimes read a TCP reset instead of GOAWAY** (`9f0e5ee`). `H2Connection.sendData`
  checked the flow-control allowance before the stream's existence. A stream the client had reset has an allowance
  of 0, so a handler's DATA still on its way gave INTERNAL_ERROR instead of STREAM_CLOSED. The driver treats
  INTERNAL_ERROR as fatal: `serveH2` failed, the worker dropped the socket without `closeGracefully`, and h2spec's
  unread frames made the kernel send a reset. Test: `sends_after_the_peer_reset_are_stream_closed`, which fails
  without the fix.
- **Open: h2spec §8.1.2.6 #1 and #2 depend on timing** (about 1 run in 10 over TLS, 1 in 4 over h2c). The example's
  `/` answers without reading the body. If its response is written before the DATA frame whose length contradicts
  `content-length` arrives, h2spec sees HEADERS where it expects RST_STREAM or GOAWAY. The stream is still reset when
  the DATA arrives. RFC 9113 §8.1 lets a server send a complete response before the request is complete. Holding
  every response until a declared-length body has ended would pass h2spec, but would delay exactly the early answers
  (401, 413) that §8.1 exists for. This is the owner's decision, since the M7 gate said "h2spec 100 %".
