## Stage 1: vendoring and the build (2026-11-09)

- **`tools/vendor_quic.py`** vendors ngtcp2 1.26.0 and nghttp3 1.19.0 into `third_party/` (2.8 MB):
  - it checks each release tarball against GitHub's recorded SHA-256 (`third_party/README.md`);
  - it copies only the compiled sources (48 and 32), their headers and their MIT licences;
  - it writes a portable `config/config.h` for each, and one wrapper per source in each package's `c/vendor/`.
  - **The wrappers exist because manifests pass no defines.** Each wrapper sets what the libraries' own build would:
    `HAVE_CONFIG_H`, the static-library macro, and `_GNU_SOURCE` on Linux. Then it `#include`s the untouched
    original.
  - **`config.h`** detects the system with the preprocessor. Only optional faster paths depend on it, and each
    library has a portable fallback (`ngtcp2_net.h`, `nghttp3_conv.h`). The libraries test `WIN32`, which compilers do
    not define, so `config.h` defines it on Windows.
- **`web_quic` (new):**
  - its shim (`c/quic_shim.c`) refuses OpenSSL < 3.5 at compile time and reports the versions;
  - its include path is upstream's for the crypto sources (`lib/` and `crypto/`, from `crypto/ossl/CMakeLists.txt`);
  - it links OpenSSL per system as `web_tls` does.
- **`web_http3`** depends on `web_core`, `web_http` and `web_quic` (Web ADR 0004 amendment 4). It has its own shim
  (`c/h3_shim.c`).
- **CI:**

  - one `ubuntu-24.04` job keeps OpenSSL 3.0 tested, sweeps included, without the two QUIC packages;

## Stage 3, part (a): what web_quic gains for HTTP/3 (2026-11-09)

The design is Web ADR 0014 amendment 4. It settles the layering question left open at stage 1: `web_http3` serves
`web_http`'s `Application`, as `web_http2` does, so neither `web_server` nor `web_http3` depends on the other.

- **`QuicConnection.openUniStream` and `QuicLink.openUniStream`**, for HTTP/3's control and QPACK streams.
- **Credit given back on consumption:** `QuicConnection.creditOnConsume`, `consume(stream, n)`,
  `QuicServerOptions.creditOnRead` (default true) and `QuicLink.consume`. The shim gives a stream's credit back only
  through `qs_consume`.

### Tests run (2026-11-09, ceesafec 0.22.0, macOS)

- **`credit_waits_for_consume` (new):**
  - Before consuming, the server never holds more than the stream's 1 MiB window of a 3 MiB stream (RFC 9000 §4.1),
    and after 300 rounds it holds exactly 1 MiB.
  - Once it consumes, all 3 MiB arrive, in order.
  - With `qs_set_manual_credit` made a no-op, it fails at "no more than the stream's window before consuming".
- **`unidirectional_streams` (new):** the client's first unidirectional stream is 2 and the server's is 3 (RFC 9000
  §2.1), and each carries its bytes across.
- **web_quic, sanitizers and sweeps:** 9 passed, with 0 failures in 1224 allocation-sweep runs and 200
  cancellation-sweep runs. `examples/hq` builds.
- **`one_direction_reset_and_stop` (new):** the server resets only its sending side (code 7), and the client's
  later bytes and FIN still arrive (RFC 9000 §3.1). The client stops reading a second stream (code 9), and the server
  is told so (§3.5).
  - Its first run failed: the server never saw STOP_SENDING. The shim had registered the event on ngtcp2's
    `stream_stop_sending` callback, which reports a local shutdown, instead of `recv_stop_sending`, the peer's frame
    (Web ADR 0014 amendment 4 item 7). It passes with the fix: web_quic 10 passed, with 0 failures in 1424
    allocation-sweep runs and 200 cancellation-sweep runs.

## Stage 3, part (b): the h3 shim and `H3Connection` (2026-11-09)

- **`web_http3/c/h3_shim.c`:** one `nghttp3_conn` per QUIC connection, server or (for the tests) client, with Web ADR
  0014 §3.4's contract:
  - an event queue drained by CeeSafe, and allocations through `CEE_ALLOC_FOREIGN`;
  - bodies held in chunks that never move until nghttp3 reports them acknowledged;
  - nghttp3's output copied into QUIC and acknowledged at once;
  - QPACK's table at 4 KiB, and 16 blocked streams.
- **`web_http3/src/connection.cee`:** `H3Connection` (sans-I/O), `H3Fields`, `H3Event`, `H3Out`, `H3Error` and
  `H3Errors.closeCode`.
- **`web_http3/src/glue.cee`:** `H3Glue` (start, onQuic, obey, flush) over `H3Streams`, which `QuicConnection` and
  `QuicLink` implement.
- **web_quic gains** `QuicTls.serverFromPem`, `clientFromPem`, `QuicError.Tls` and
  `QuicConnection.peerApplicationClose`.
- **What the first runs corrected** (amendment 4 item 3):
  - **A malformed request closes the connection** with H3_MESSAGE_ERROR. nghttp3 allows nothing more after a read
    error, so it is a connection error, which RFC 9114 §8 allows; it is not a stream reset.
  - **QUIC's events go to nghttp3 before the handshake ends too.** The first harness dropped them, and the server failed
    with H3_CLOSED_CRITICAL_STREAM (-605).

### Tests run (2026-11-09, ceesafec 0.22.0)

The tests are in memory: two `QuicConnection`s on a fake clock, with `H3Connection` client and server over `H3Glue`
(`web_http3/tests/memory.cee`).

- **`get_and_its_answer`:**
  - the server sees `:method`, `:scheme`, `:authority` and `:path` in the order sent, and the stream's end with them;
  - the client sees `:status: 200`, then `content-type`, the body "hello, h3", and the end.
- **`large_bodies_both_ways`:** a 3 MiB request body answered with 3 MiB, past the body queue (256 KiB), QUIC's

- **`a_malformed_request_closes_the_connection`:** a request without `:path` (RFC 9114 §4.3.1) makes the server close

- **`trailers_both_ways`:** each side's trailer fields arrive apart from its head, after the body.
- **`contexts_from_pem` (web_quic, new):** the PEM constructors complete a handshake with ALPN h3, and a key that is
  not PEM is refused with `QuicError.Tls`.

## Stage 3, part (d): the guards and the drain (2026-11-09)

## CI's Linux sanitizer job (2026-11-10)

Ubuntu 26.04's ASan, UBSan and sweep step was shut down partway on every run since that job was added ("Release",
above). Pull request #7 made `tools/run_tests.py` print each run as it ends and the step log memory each minute.

- **What the next run showed:** 65 s into `web_http3`'s allocation sweep, memory went from 1.1 GB to all 16 GB and
  2.2 GB of swap, and the runner was shut down. Disk stayed at 89 GB free.
- **Reproduced** in an `ubuntu:26.04` container on hanan (gcc 15.2.0, Ubuntu's OpenSSL 3.5.5), capped at 6 GB:
  `early_data_runs_safe_requests_only` with allocation 9772 failing was killed by the cap (status 137). Under gdb, the
  process grew by about 250 MB a second inside `SSL_CTX_free` → `SSL_CTX_flush_sessions_ex` → `OPENSSL_LH_delete`,
  called from `qs_tls_free` when the server's `QuicTls` was dropped.
- **The cause is OpenSSL's.** In 3.5.5, `SSL_CTX_add_session` put a session on the cache's list even when inserting it
  in the hash table failed for want of memory, so the list and the table disagreed and the flush never ended.
  OpenSSL fixed it in 3.5.6 (commit `47eeebe`, "Fix error handling in SSL_CTX_add_session": "An out-of-memory error
  in lh_SSL_SESSION_insert could trigger various use-after-free errors", openssl/openssl#28632). hanan's OpenSSL is
  3.5.9, which is why its sweeps never showed it: there, the same tree's `web_http3` sweep peaked at 245 MB.
- **The same container's other sweep failures:** in `rapid_reset_closes`, a failed allocation inside 3.5.5's
  `OPENSSL_init_ssl` leaked 407 bytes of OpenSSL's own (LeakSanitizer, exit 1). One run of `six_requests_over_udp`
  failed, and passed when run again alone.
- **Ours:** UBSan reported `memcpy` from a null pointer with length 0 (`quic_shim.c` and `h3_shim.c`, an event queue
  whose data buffer was never allocated). Harmless in practice, undefined in C; both now copy only a non-empty event.
- **The change to CI:** the 26.04 sanitizer job builds OpenSSL 3.5.9 from source (the release tarball, its SHA-256
  pinned, cached) and links its sweeps against it. Its other steps, and the io_uring job, keep Ubuntu's 3.5.5.
- **For users:** an out-of-memory error while caching a session (0-RTT's single-use tickets, or resumption) can
  corrupt OpenSSL 3.5.0–3.5.5's session cache. Prefer OpenSSL 3.5.6 or later; the minimum stays 3.5, which Ubuntu
  26.04 ships as 3.5.5.

## Fuzzing the QUIC shim (2026-11-11)

Web ADR 0015 §3 builds the harness this milestone left out (above, "Not yet done").

- **The harness:** `tests/fuzz/quic/fuzz_quic.c` runs a client and a server `qs_conn` in one process, made and
  driven as web_quic makes and drives them, with the listener's path before the server exists: Version Negotiation,
  Retry, `qs_conn_server`, and stateless resets after it is gone. The input controls the network between them
  (delivery, loss, duplicates, reordering, corrupted bytes, datagrams of its own), the clock, and stream operations
  on either side: open, write, reset, stop reading, give back credit, migrate, close.
- **Packet protection:** the input's first byte chooses it.
  - **Real protection:** corrupted and injected datagrams stop at the AEAD. Stream data is then an oracle: each side
    writes a known pattern, and every byte received is checked, with its order and its end.
  - **Null protection:** the harness compiles the shim into itself and replaces its three packet protection
    callbacks with ones that copy, as ngtcp2's own tests do. The handshake still runs, so the input's frames reach
    ngtcp2's parser and every callback of the shim, as an authenticated but hostile peer's would. The shim's source
    is not changed for this; three macros replace the callbacks before it is included.
- **Other invariants:**
  - every allocation of the shim and ngtcp2 is counted, and none is left when both connections are freed;
  - one allocation can be made to fail;
  - every result is within its buffer or a known code;
  - every event and ID change is of a known kind.
- **Determinism:** OpenSSL's randomness comes from a generator seeded the same for every input, through it ngtcp2's
  and the handshake's, so an input replays exactly.
- **Seeds:** nine scripts (`--seeds`): a handshake; streams both ways; loss, reordering and corruption; migration;
  close; Retry; manual credit; and two with null protection, one with frames the input wrote.
- **What it found:** `qs_retry_check` passed the Initial's destination ID, the peer's choice, to
  `ngtcp2_pkt_write_retry`. That function asserts the ID differs from the Retry's new one, and the vendored ngtcp2
  keeps its assertions, so a match would end the process.
  - **Reachability:** in web_quic the new ID is 20 fresh random bytes per Initial (`QuicRetry.check`,
    `packages/web_quic/src/connection.cee`), so a peer would have to guess 160 bits. It was reachable here only
    because the harness's ID was fixed.
  - **The fix:** the shim now drops such an Initial (`qs_retry_check` returns 0) before calling ngtcp2. The
    harness's listener draws a fresh ID per Initial, as web_quic does; operation 14 keeps a fixed one, so the guard
    stays exercised.

## Resumption and 0-RTT in the QUIC fuzzer (2026-11-12)

The harness above left out resumption and 0-RTT. It now covers them, and found two defects in the shim.

- **What it does now:**
  - Mode bit 6 makes the server accept 0-RTT (`qs_tls_allow_early`, web_quic's `allowEarlyData`).
  - Operation 15 on the client with argument bit 1 set reconnects, as a client of web_quic does on its next visit.
    It keeps the client's ticket (`qs_ticket`) and frees both connections. A new client then resumes
    (`qs_resume`) from the newest ticket, the first one (a replay), or none.
  - Streams that the new client opens and writes before its handshake ends go out as 0-RTT.
  - The server's session cache, which holds the single-use tickets, is emptied before each input. The harness
    checks that it is.
- **New invariants:**
  - after both handshakes, the client and the server agree on `qs_resumed` and `qs_early_accepted`;
  - a server without 0-RTT never accepts early data, and early data is accepted only on a resumed connection;
  - with 0-RTT on, a ticket resumes at most one connection, because OpenSSL's replay protection makes tickets
    single-use (Web ADR 0014 §3.7, amendment 5 item 5);
  - `qs_resume` on a ticket from `qs_ticket` returns 1 when the server allows 0-RTT, else 0.
- **Rejected early data:** ngtcp2 sends it again in 1-RTT by itself. The shim never calls
  `ngtcp2_conn_tls_early_data_rejected`, so the stream data check holds through a rejection. A trace of the `early`
  seed shows it: the replayed ticket's 1,024 bytes reach the server after the full handshake.
  - `QuicConnection.earlyDataAccepted`'s documentation said the application must send rejected early data again.
    That would send it twice. The documentation is corrected (`packages/web_quic/src/connection.cee`, `docs/api`).
- **Seeds:** four more: `resume`, `early`, `early-retry` and `early-null`. Each makes a first connection, resumes
  with 0-RTT and writes early, then replays the first ticket.

### What it found

1. **A use-after-free in the shim, on a client.**
   - **The shim's side:** `qs_stream_reset` and `qs_stream_reset_sending` freed the stream's bytes at the reset.
     `ngtcp2_conn_writev_stream`'s documentation asks the application to keep them until they are acknowledged or the
     stream is closed, and in one sequence ngtcp2 read them later (ASan, heap-use-after-free in `ngtcp2_cpymem`).
   - **Upstream:** the sequence is reported privately to ngtcp2 (2026-11-12), as its `SECURITY.md` asks. Its details
     and a regression test in `packages/web_quic/tests/loopback.cee` are added here once ngtcp2 has answered.
   - **The fix:** a reset now marks the stream. It takes no more bytes, `qs_write` skips it, and `qs_all_acked` does
     not wait on it. Its bytes stay until `stream_close` or `qs_conn_free` releases them. They were already bounded
     per stream (`QS_STREAM_HOLD`).
2. **An assertion in ngtcp2, reachable through `qs_ticket`.**
   - **The sequence:** asked for a ticket on a resumed connection before its handshake ends, `qs_ticket` found the
     session resumable and asked ngtcp2 for the server's transport parameters. ngtcp2 does not have them yet, and
     `ngtcp2_conn_encode_0rtt_transport_params2` asserts that it does.
   - **Reachability:** `QuicConnection.ticket` is public and may be called at any time, so this was an abort
     reachable through a safe API.
   - **The fix:** `qs_ticket` returns 0 until the handshake completes, as its comment already promised.

### What the traces found: a ClientHello's second datagram that comes first costs the client a second

- When the Initial's first datagram is lost, the server makes a connection from the second, and that connection
  reads one packet and sends nothing: 8 times in the 20 traces.
- ngtcp2 asks for a Retry there (`third_party/ngtcp2-1.26.0/lib/ngtcp2_conn.c:10426`: the first Initial read does

  for that code, so the connection ends and nothing is sent. The 0-RTT datagrams held for it go with it.
- The client sends its Initial again at its first probe timeout, 1,008 ms later in the trace read, and the server
  makes a second connection. The handshake then completes, and all the early bytes come in 1-RTT.
- Nothing is lost and no state is kept, so this is a delay, not a failure. A client whose ClientHello spans two
  datagrams (a resuming one here) pays it whenever the first is lost, or is overtaken by the second.
- **Not changed here.** Sending the Retry ngtcp2 asks for, or keeping the datagram for the first, is a decision
  for Web ADR 0014. Fixed since: amendment 10 ("A Retry for a ClientHello without its start", below).

## A Retry for a ClientHello without its start (2026-11-13)

Web ADR 0014 amendment 10: the fix for what the traces found.

- **`QuicError.RetryWanted`** is ngtcp2's `NGTCP2_ERR_RETRY`, from a server connection's first `feed`
  (`packages/web_quic/src/connection.cee`, `qs_error_kind` in `packages/web_quic/c/quic_shim.c`).
- **The connection's task answers it with a Retry** and ends (`retryInstead` in
  `packages/web_quic/src/server.cee`). The client sends its whole Initial again at once, with the token.
- **The test:** `a_clienthello_without_its_start_gets_a_retry` in `packages/web_quic/tests/held.cee`, over real
  UDP, with the resumed client of the 0-RTT test (an Initial of two datagrams, then 4,000 early bytes).

    sent whole.
  - Expected (RFC 9000 §8.1 and §7.3): for the first two, the client sees a Retry (`retried()`: the server's
    transport parameters carry the Retry's ID), and the server counts all 4,000 bytes, right. For the third, no
    Retry, and every byte early.
  - Whether the bytes are early after a Retry is the client's choice (§8.1.2), so the test expects only their sum.

## A token counts only when it was checked (2026-11-14)

Web ADR 0014 amendment 11: the fix for the finding above.

- **The fix** is in `qs_conn_server` (`packages/web_quic/c/quic_shim.c`): ngtcp2 is given the Initial's token only
  when the caller has the original destination ID from a token that verified (`QuicConnection.serverAfterRetry`).
  No CeeSafe source changed, and no public API.
- **The test:** `an_unchecked_token_validates_nothing` in `packages/web_quic/tests/loopback.cee`, sans-I/O.
  - A client is sent a Retry and puts its token in its next Initial. That first flight makes two server
    connections, which then hear nothing more: one after `QuicRetry.check` (`serverAfterRetry`), one without the
    check (`server`). Each sends what it has, and again at each of its next 6 timers.
  - Expected (RFC 9000 §8.1): the unchecked one sends at most three times what the client sent. The checked one
    sends more, which shows the count can tell them apart.
  - The token in the test is a real Retry token that the caller did not check. A token without the Retry mark,
    over the listener, takes the same path in the shim; no client here can send one, so that is not tested.
