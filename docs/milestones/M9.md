## Findings

1. **Byte-at-a-time copies.** `OwnedBuffer.append` (`packages/web_core/src/buffer.cee:89`) copies with a loop of
   single-byte stores, and is the top function streaming 1 MiB over HTTP/1.1 (44 % of samples) and HTTP/2. CeeSafe has
   had `SliceMut.copyFrom` since 0.1.0 (type system §16.5): one length check and one `memcpy`.
2. **Byte-at-a-time zeroing.** `OwnedBuffer.create` (`buffer.cee:16`) fills its vector with one `push(0)` per byte. Each
   HTTP/2 stream creates a 16 KiB write buffer and a 4 KiB response head (`packages/web_http2/src/serve.cee:832`,
   `:836`), about 20 000 pushes a request; that is the top function for h2c `/small`. `Vector.resize(n, 0)` (CeeSafe
   0.15.0, ADR 0071) does it at once; a pool (stage 2) avoids it altogether.
3. **`Exchange.remaining()` over HTTP/2 is null** even when the request declares `content-length`
   (`packages/web_http/src/exchange.cee:388`: a stream body is `BodyState.Stream`). The benchmark's `/echo` then makes
   a 1 MiB buffer per request (`benchmarks/http/src/main.cee:64`), which explains h2c `/echo` at 2 k req/s against
   43 k over HTTP/1.1. The request's head carries the declared length (RFC 9113 §8.1.1), so `remaining()` can report it.
4. **HTTP/2 allocates per request** (38 for h2c `/small`, 0 for HTTP/1.1): the stream's task, channels and buffers. A
   1 MiB `/stream` costs 867 (h2c), 1 452 (TLS) allocations: one or more per DATA frame.
5. **TLS `/stream`**: 775 allocations per 1 MiB over HTTP/1.1, OpenSSL's (clear-text HTTP/1.1 makes none).

6. **Open: one hang of `a_silent_client_hits_the_handshake_deadline`** (web_tls, native, 2026-11-07), not reproduced
   in 1 000 runs since (stage 2, below).

Findings 1–3 are fixes to make before stage 2's measurements: until they are made, they hide what pooling and vectored
writes would change.

### HEADERS and DATA in one write (2026-11-07)

**Why.** A stream's DATA needs flow-control credit from the connection task (`Outgoing.WantSend`, then a grant), so a
response takes at least two turns of the connection loop, and each turn wrote its output: HEADERS in one `sendto`,
DATA in the next. Each turn also raced a fresh socket read against the streams' channel; on kqueue a read tries
`read()` at once, and on `EAGAIN` adds a one-shot filter that its cancellation deletes (CeeSafe's
`runtime/hosted/ceesafe_rt_async.c:3590`, `:554`, `:594`): an empty read and two filter changes whenever a stream's
message won.

**Change** (`packages/web_http2/src/serve.cee`, `run`). A turn that leaves credit granted and not yet used (`total > 0`)
does not write, and waits only on the streams' channel, for at most 10 ms: the granted streams are waiting in `write`
with their bytes, so their DATA comes at once, and the next turn writes HEADERS and DATA together. At most one turn in
a row is deferred. web_http2's 52 tests and its cancellation sweep (884 runs) pass.

`eddfa80` added `Transport.sendFile` and `Exchange.sendFile` (Web ADR 0013 §3.3, as amended in §7):

- `TcpTransport` hands the file to lib/std's `AsyncTcpStream.sendFileAll` (`sendfile` in the kernel). `TlsTransport`,
  `MockTransport` and the test doubles read it and write it (`Transports.copyFile`); HTTP/2 reads it and sends DATA
  (`Exchange.streamFile`).
- `Exchange.sendFile` sends 1 MiB slices, each within `writeTimeoutMs`; a chunked response sends a chunk per slice.
  HEAD, 1xx, 204 and 304 count the bytes and send none.
- A file shorter than promised fails the send, and the exchange is then done and not kept: no last chunk over HTTP/1.1,
  no END_STREAM over HTTP/2, even if the handler ignores the error.
- `benchmarks/http` gains `GET /file` (a 1 MiB file, `CW_FILE`), and `run.py` the route `file`, served by nginx from
  the same bytes.

### Tests run

- `packages/web_server/tests/sendfile.cee`, nine tests (expected bytes built in the test from the file's pattern, not
  by the code under test): HTTP/1.1 with a length, chunked across a slice boundary (1 048 586 bytes after a 1-byte
  write: chunks `1`, `100000`, `a`, then the last chunk), HEAD, a short file with and without a length, HTTP/2 DATA
  with END_STREAM, and a short file over each with the handler ignoring the error. With `done = true` removed from
  `Exchange.sendFile`'s failure path, only the last two failed; they are why they exist.
- `python3 tests/interop/sendfile.py` (2026-11-07): a 1 GiB file of random bytes through curl 8 (Homebrew's, OpenSSL
  and nghttp2; macOS's LibreSSL 3.3.6 refuses the P-256 test certificate) over HTTP/1.1, TLS with HTTP/1.1, h2c and
  h2. SHA-256 computed by Python's hashlib on both sides: `6441d79a…f0473975c` for all four, 1 073 741 824 bytes,
  content-length as declared. A 256 MiB file truncated to 64 MiB one second into a rate-limited transfer: curl got
  exactly 67 108 864 bytes and exited 18 (HTTP/1.1, both) or 92 (HTTP/2, both). 16/16.
- Full suite with ceesafec 0.19.1, `--sanitize --alloc-sweep --cancel-sweep`: 43 runs passed, 0 failed, 1 skipped
  (web_tls in the interpreter, which cannot run its C), on `eddfa80` and again on the 256 KiB change below; the
  interop again on that change at 64 MiB (`--size-mib 64`): 16/16.

### 256 KiB pieces

(`Transports.fileBuffer`: the file's length if less). HTTP/2's `sendData` already splits a piece by the window

At 100 connections every mode is now faster from a file than from memory (the other counts were not rerun for
`/stream`). Peak RSS at 100 is higher than `/stream`'s by 1.6 MiB over HTTP/1.1 in clear (no buffer: `sendfile`),
28–29 MiB over HTTP/2 (about the buffers, 100 × 256 KiB = 25 MiB) and 57 MiB over TLS with HTTP/1.1, whose share
above the buffers is not yet explained. nginx is
still ahead over TLS with a file (stage 1's note: eight processes against one thread).

and `ab-256k-*` (the A/B), `256k-stream-file.json` (both routes with allocations).
