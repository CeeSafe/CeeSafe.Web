# M7 — HTTP/2: record

Implementation plan §7 (M7). Toolchain: ceesafec **0.10.3** (0.10.1 at first; B16 and B17 needed 0.10.2 and 0.10.3). Design: Web ADR 0011, accepted 2026-11-03 with the
owner's four answers (TLS ALPN `h2` and cleartext `h2c` by prior knowledge; server only; priority ignored; push
supported), amendment 1.

**Status (2026-11-03):** in progress, on branch `m7-http2`. Stages 1 (engine) and 2 (driver, `web_server` entry) are
done. Stage 3 (the gate) passes every check below, on 0.10.3. CeeSafe's B16 (a lost wake past ~30 connections) was
fixed in 0.10.2, and B17 (throughput past ~2 000 concurrent streams) in 0.10.3 (ADR 0062). Merged to main and released
as v0.3.0 (the owner, 2026-11-03).

**Correction (2026-11-04, released as v0.3.1):** the 145/145 below was a single run. Repeated runs in M8
(`docs/milestones/M8.md`, on the M8 branches) failed 8 of 30 against v0.3.0. Two causes:
- §5.1 #10, about 1 run in 100: a bug. DATA for a stream the client had reset gave INTERNAL_ERROR, which ended the
  whole connection with a TCP reset instead of GOAWAY. Fixed in v0.3.1 (test
  `sends_after_the_peer_reset_are_stream_closed`).
- §8.1.2.6 #1 and #2, about 1 run in 10 over TLS: a timing case, kept by the owner's decision. The example answers
  before the malformed DATA arrives, which RFC 9113 §8.1 allows. The gate's "h2spec 100 %" is read as every case
  passing when the response does not race the request's body.

v0.3.1's runs (2026-11-04, macOS arm64, ceesafec 0.10.3, the release tree): h2spec 2.0.0 `-t -k` against
`examples/https`, §5.1 #10 alone 300 times: 0 failed. The whole suite 30 times: 26 runs 145/145, 4 failed only
§8.1.2.6 #1 or #2; the server's report counted 4 771 connections, 0 failed. `python3 tools/run_tests.py --sanitize
--alloc-sweep --cancel-sweep`: 39 runs passed, web_tls's interpreter run skipped. `ceesafec check` and `fmt --check`
clean on every package and on `examples/server` and `examples/https`.

## Gate (Web ADR 0011 §5)

| Check | State |
|---|---|
| h2spec 100 % | done over TLS (145/145 in one run; see the correction above) |
| h2load interop | done: with ceesafec 0.10.3, 68 880 to 75 812 req/s from 10 × 100 to 50 × 100 streams, 37 297 at 100 × 1; 0 failed (table below) |
| curl `--http2` and nghttp | done, h2c and TLS |
| flow-control and cancel stress (a stream cancelled mid-body; the connection cancelled with 100 streams) | done: `tests/stress.cee`, plus a hundred drained and the window tests |
| a fuzz target over the engine | done: `tests/fuzz/h2`, 30 min clean under the sanitizers, mutants caught |
| sweeps over `web_http2` | done |

The fuzzer's invariants (`tests/fuzz/h2/src/main.cee`), none taking the engine as its own oracle:
1. the same events, connection error and output whether the input is fed whole or in random pieces;
2. whole frames out, none over 16 384 bytes (RFC 9113 §4.2);
3. requests on odd streams, each above the last (§5.1.1);
4. each request's fields pass §8.2-§8.3, checked by the fuzzer's own code (lowercase names, pseudo-fields first and
   known, one `:method`, `:scheme` and a non-empty `:path` unless CONNECT, no connection-specific field, `te` only
   "trailers");
5. with nothing consumed, no stream gets more DATA than 65 535 bytes, nor the connection more than it opened (§6.9);
6. HPACK and Huffman round trips (RFC 7541), and damaged blocks decode the same way twice.

The stress tests' expected values come from RFC 9113: a 1 000-byte initial window allows exactly 1 000 bytes
(§6.9.2); WINDOW_UPDATEs of 99 000 (stream) and 34 465 (connection, from 65 535) allow exactly 100 000; GOAWAY on a
drain names the last stream processed (§6.8).
